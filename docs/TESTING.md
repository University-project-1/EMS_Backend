# دليل الاختبارات في EMS

## الهدف ومعيار الجودة

تشكل الاختبارات في EMS **شبكة أمان متعددة الطبقات** وليست مجرد فحوصات لمسارات HTTP. وهي مصممة لاكتشاف انكسار العقود العامة، وأخطاء المصادقة والصلاحيات، وانكشاف بيانات دور أو شركة إلى دور آخر، وتراجع السلوك في الرحلات الأساسية. يجب أن يبقى كل اختبار مستقلاً وقابلاً للتكرار، وأن يعبّر اسمه عن قاعدة أعمال واضحة قابلة للفهم من دون قراءة التنفيذ الداخلي.

> إضافة مسار جديد تدخل تلقائياً في فحوصات العقد والسلامة العامة. أما السلوك التجاري الخاص بالمسار، مثل التحقق والملكية وانتقال الحالات، فيحتاج اختباراً تفصيلياً مقصوداً ضمن وحدة العمل المناسبة.

| الطبقة | الغرض | آلية التوسع |
|---|---|---|
| اختبارات العقود | التحقق من المسارات و`Form Requests` و`Enums` والمخطط وبنية استجابات API | تكتشف العناصر الجديدة تلقائياً عند إضافتها إلى المشروع |
| اختبارات السلامة | منع 5xx والتحقق من الحماية الأساسية ومسارات القراءة والكتابة | تغطي المسارات الحالية وتكشف الانحدارات العامة |
| اختبارات السلوك | تثبيت النجاح والفشل والتحقق والملكية وحالات الموارد غير الموجودة | يضاف اختبار واضح لكل قاعدة أعمال جديدة |
| اختبارات الخدمات والسياسات | التحقق من العزل بين الأدوار والإشعارات وانتقالات الحالات | توسع باختبار السياسة أو الإشعار المتأثر |
| اختبارات الرحلات المتكاملة | ربط إجراءات الأدوار المتعددة في سيناريو إنتاجي واحد | تضاف عند إنشاء رحلة أعمال جديدة أو تغيير تسلسلها |

## تشغيل الاختبارات محلياً

يشغّل الأمر التالي جميع اختبارات المشروع باستخدام SQLite داخل الذاكرة كما هو محدد في `phpunit.xml`.

```bash
composer test
```

لتشغيل ملف أو مجموعة محددة أثناء التطوير يمكن استعمال الأمر التالي.

```bash
php artisan test --compact tests/Feature/VisitorReviewTest.php
```

يطبق التنسيق على اختبار أو مجموعة اختبارات جديدة قبل إدراجها في المراجعة.

```bash
vendor/bin/pint tests/Feature/VisitorReviewTest.php
```

ينشئ أمر التغطية تقرير Clover في `coverage/clover.xml` ويطبق حد التغطية الابتدائي. يحتاج هذا الأمر إلى محرك تغطية PHP مثل PCOV أو Xdebug. لا يتوفر محرك التغطية في بيئة Laragon المحلية الحالية؛ ولذلك يبقى `composer test` هو تحقق التشغيل المحلي الموثوق، بينما ينفذ تقرير التغطية في GitHub Actions عبر PCOV.

```bash
composer test:coverage
```

| الأمر | الاستخدام | النتيجة المتوقعة |
|---|---|---|
| `composer test` | التحقق اليومي قبل الالتزام | نجاح جميع الاختبارات بلا فشل |
| `vendor/bin/pint tests/Feature/...` | تنسيق اختبار جديد أو معدّل | عدم وجود مخالفات Pint |
| `composer test:coverage` | قياس التغطية في بيئة تحوي PCOV أو Xdebug | ملف `coverage/clover.xml` وحد تغطية لا يقل عن 5% |

## التكامل المستمر

ينفذ ملف `.github/workflows/tests.yml` الحزمة عند كل `push` و`pull request`. تجهز المهمة PHP 8.3 مع PCOV، وتثبت الاعتمادات، وتولّد مفتاح التطبيق ومفاتيح Passport، ثم تشغّل الاختبارات العادية وتقرير التغطية. يحفظ التقرير الناتج كـ artifact باسم `php-coverage-clover` يمكن تنزيله من صفحة تشغيل GitHub Actions.

حد التغطية الحالي **5%** هو حد تأسيسي يمنع فقدان التغطية كلياً عند بداية تطبيق القياس. يجب رفعه تدريجياً بعد قراءة أول تقرير صادر من CI، وبشكل متوافق مع التغطية الواقعية، لا عبر وضع رقم تخميني يوقف الخط دون فائدة.

## مصفوفة التغطية الحالية

| الوحدة | الاختبارات التفصيلية الرئيسة | القواعد المثبتة |
|---|---|---|
| المصادقة والأدوار | `MobileAuthTest`, `SystemUserAuthenticationTest`, `SystemUserRoleIsolationTest` | تسجيل الدخول والخروج، منع دخول المدير كعارض والعكس، عزل الحراس والأدوار |
| العارض | `ExhibitorProfileTest`, `ExhibitorCompanyTest`, `ExhibitorEventTest`, `ExhibitorBoothTest`, `ExhibitorInvitationTest`, `ExhibitorLeadTest` | تحديث الملف، عرض الشركة، ملكية الأحداث والأكشاك، حماية الدعوات وسجل الاهتمامات |
| الزائر | `VisitorSavedItemsTest`, `VisitorLeadHistoryTest`, `VisitorEventTest`, `VisitorReviewTest`, `VisitorReportTest` | العناصر المحفوظة، منع حفظ فعالية غير معتمدة أو كشك غير محجوز، إخفاء الأحداث غير المعتمدة، التقييمات والتقارير والتحقق والإشعارات |
| الإدارة | `AdminDashboardTest`, `AdminAnnouncementTest`, `AdminReportTest` | بنية لوحة التحكم، إنشاء الإعلان والتحقق منه، حل التقرير ومنع إعادة معالجته |
| الرحلات المتكاملة | `EventLifecycleE2ETest` | ظهور فعالية العارض، تفاعل الزائر معها، ثم معالجة المدير للتقرير |
| العقود والبذر | اختبارات `Contracts/*` و`Seeders/DatabaseSeederCoverageTest` | توافق المسارات والنماذج والتعدادات والطلبات والاستجابات والـ Seeder |

## إضافة ميزة جديدة بصورة صحيحة

عند إضافة ميزة جديدة، يبدأ العمل بتحديد قاعدة الأعمال التي يجب ألا تنكسر. يضاف المسار تلقائياً إلى طبقة العقد، لكن يجب إنشاء اختبار سلوكي يثبت حالة النجاح، وأخطاء الإدخال المهمة، وهوية المستخدم أو ملكية المورد عند وجودها، والحالة الحدية أو الانتقال بين الحالات. إذا كانت الميزة ترسل إشعاراً أو تستخدم Policy أو Service، يضاف تحقق صريح من النتيجة الملحوظة مثل المستلم الصحيح للإشعار أو رفض الوصول لمورد أجنبي.

تستخدم اختبارات الأدوار Trait `Tests\Support\CreatesActors` لإنشاء مدير أو عارض أو زائر. ويجب اعتماد `actingAs($user, 'system')` لمستخدمي النظام و`actingAs($user, 'mobile')` للزوار، مع تجنب الاعتماد على ترتيب تشغيل الاختبارات أو بقايا بيانات اختبار آخر.

| نوع التغيير | الحد الأدنى للاختبار المطلوب |
|---|---|
| Endpoint جديد | نجاح، مصادقة، صلاحية الدور، وتحقيق API contract التلقائي |
| إنشاء أو تعديل بيانات | نجاح، قواعد تحقق، تأكيد قاعدة البيانات، وعزل الملكية إن وجدت |
| انتقال حالة | الانتقال المسموح، رفض الانتقال غير الصحيح، وصاحب الإجراء المسجل |
| إشعار | استخدام `Notification::fake()` والتحقق من المستلم ونوع الإشعار |
| علاقة جديدة أو Seeder | إنشاء بيانات مترابطة وتحديث اختبار تغطية البذر أو المخطط عند الحاجة |

## قواعد التنظيم

يبقى كل اختبار ضمن `tests/Feature` أو `tests/Feature/Contracts` بحسب طبقته. تستخدم أسماء ملفات مرتبطة بوحدة العمل مثل `ExhibitorEventTest` و`AdminReportTest`، وتستخدم أسماء حالات تصف النتيجة المتوقعة مثل `exhibitor can list events belonging to their assigned company only`. لا يستخدم الاختبار أرقام تعريف ثابتة من بيانات محلية ولا يتصل بخدمات خارجية.

عند تعديل API envelope يجب الحفاظ على المفتاح `status` كما هو معتمد في التطبيق. وعند اختبار Pagination ينبغي التحقق من البنية المناسبة لنوع pagination المستخدم؛ فبعض المسارات تستخدم `data.data` بسبب cursor أو length-aware pagination.

## قائمة التحقق قبل المراجعة والرفع

| التحقق | الحالة المطلوبة |
|---|---|
| تشغيل `composer test` | ناجح |
| تطبيق Pint على الملفات الجديدة أو المعدلة | ناجح |
| اختبار النجاح والفشل والملكية للميزة | موجود عند الاقتضاء |
| اختبار الإشعار أو Policy أو Service المتأثر | موجود عند الاقتضاء |
| تحديث هذا الدليل ومصفوفة التغطية | مكتمل عند إضافة وحدة جديدة |
| مراجعة GitHub Actions وتقرير Clover | مكتمل بعد الرفع |
