# دليل الاختبارات في EMS

## الهدف

تعمل مجموعة الاختبارات كخط أمان للمشروع. يُعدّ نجاح `composer test` مؤشراً موحّداً على أن السلوكيات المغطاة، وعقود الواجهة البرمجية، وبيانات الاختبار الأساسية ما زالت سليمة بعد أي تعديل. تُستخدم قاعدة بيانات SQLite مؤقتة في الذاكرة، لذلك تبقى الاختبارات مستقلة ولا تعدّل بيانات بيئة التطوير.

| الأمر | الاستخدام | النتيجة المتوقعة |
|---|---|---|
| `composer test` | تشغيل كامل المجموعة | يجب أن ينتهي بنجاح قبل الدمج أو النشر. |
| `composer contracts` | تشغيل اختبارات العقود السريعة فقط | يستخدم أثناء تطوير واجهة، طلب، أو تعداد جديد. |
| `php artisan test --compact --filter="اسم الاختبار"` | إعادة تشغيل سيناريو محدد | يستخدم أثناء إصلاح اختبار أو سلوك واحد. |
| `php artisan test --compact tests/Feature/...` | تشغيل ملف أو مجلد محدد | يستخدم أثناء العمل على ميزة واحدة. |

## بنية المجموعة

تُحفظ اختبارات السلوك في `tests/Feature`، لأنّها تُشغّل التطبيق ضمن سياق Laravel الحقيقي. تختبر الملفات القائمة مسارات العمل الأساسية، والإشعارات، وبيانات البداية. تضيف `tests/Feature/Contracts` طبقة حارسة عامة تتوسع تلقائياً عند إضافة أصناف أو مسارات جديدة.

| الاختبار | ما يحميه | كيف يتوسع تلقائياً |
|---|---|---|
| `ApiRouteContractTest` | سلامة ربط مسارات API بالمتحكمات، اصطلاح الأسماء، الحراس، ومنع الوصول غير المصادق عليه للمسارات المحمية بلا معاملات URI. | يقرأ جدول المسارات عند التشغيل، لذلك تدخل المسارات الجديدة في الفحص تلقائياً. |
| `EnumContractTest` | قابلية تحميل تعدادّات التطبيق، وعدم تكرار القيم المدعومة أو فراغها. | يكتشف كل ملف في `app/Enum`. |
| `FormRequestContractTest` | قابلية تحميل طلبات الإدخال، ووجود تفويض وقواعد صريحة في `FormRequest`، وصحة مزوّدات القواعد المشتركة. | يكتشف كل ملف في `app/Http/Requests`. |

> اختبارات العقود لا تغني عن اختبارات الميزة. وظيفتها اكتشاف الانكسارات الهيكلية مبكراً، بينما تثبت اختبارات الميزة سيناريو العمل الذي يراه المستخدم.

## إضافة ميزة جديدة

ابدأ بإنشاء اختبار Pest للسيناريو الذي تريد حمايته، ثم نفّذ الميزة حتى ينجح الاختبار. استخدم الأوامر التالية بدلاً من إنشاء الملفات يدوياً:

```bash
php artisan make:test --pest FeatureName/FeatureNameTest
php artisan make:test --pest --unit ValueObjectTest
```

يجب أن يثبت اختبار كل مسار جديد، بالحد الأدنى، حالة النجاح وحالة رفض الوصول أو التحقق من الإدخال. عند إضافة `FormRequest` أو `enum` أو مسار API لن تحتاج إلى تسجيله يدوياً في اختبارات العقود؛ سيظهر تلقائياً في الفحوصات. وعند وجود منطق أعمال في خدمة، يُفضَّل اختبار النتيجة وتغييرات قاعدة البيانات والأحداث أو الإشعارات المتوقعة، بدلاً من اختبار تفاصيل التنفيذ الداخلية.

| نوع التغيير | الحد الأدنى من الاختبارات المطلوبة |
|---|---|
| مسار API جديد | نجاح مصادق عليه، رفض الوصول غير المسموح، وأخطاء التحقق. |
| خدمة أو عملية أعمال | النتيجة المتوقعة، سلامة تغييرات البيانات، والحالات الحدّية. |
| سياسة أو دور جديد | الدور المسموح والدور المرفوض، مع اختبار عدم تجاوز العزل بين المستخدمين. |
| إشعار أو حدث | المستلمون الصحيحون، نوع الإشعار، وعدم الإرسال للحالات غير المؤهلة. |
| ترحيل أو علاقة بيانات | إنشاء البيانات، القيود، والعلاقات المطلوبة. |

## التشغيل المستمر

يشغّل ملف GitHub Actions الموجود في `.github/workflows/tests.yml` الأمر `composer test` على كل `push` و`pull request`. لذلك لا ينبغي دمج أي تعديل عندما تكون نتيجة الفحص حمراء. محلياً، شغّل `composer test` قبل إنشاء طلب الدمج؛ وعند فشل الاختبار، أصلح سبب الفشل أو حدّث الاختبار فقط إذا تغيّر السلوك المقصود والموافق عليه.
